# Инструкции для проекта Autumn

## Контекст

- Проект — 3D RPG на Unity с low poly графикой и видом сверху под наклоном.
- Для генерации low poly 3D-моделей использовать Blender.
- Данж процедурно собирается из заранее сгенерированных комнат. Основной референс — Stoneshard.
- Визуальные референсы для генерации low poly 3D-моделей — Never Return, Unexplored 2: The Wayfarer's Legacy и Stoneshard.
- Целевое направление — хардкорная RPG в тёмном фэнтезийном сеттинге. Конкретные механики сложности и детали сеттинга определяются отдельно.
- Референс не задаёт автоматически сюжет и набор механик. Не переносить требования и игровой контент из других проектов только из-за похожей кодовой основы.
- Проект находится на ранней стадии. Пока не писать новые тесты. Бизнес-логику проектировать так, чтобы её можно было тестировать в дальнейшем.
- В начале работы прочитать `README.md` и `docs/architecture.md`. При реализации механики изучить ближайшие существующие примеры.

## Принципы разработки

- Соблюдать SOLID и GRASP, лучшие практики C# и Unity.
- Предпочитать простые и поддерживаемые решения без избыточных абстракций. Не создавать интерфейсы и слои только ради формального соблюдения принципов.
- Сохранять существующие соглашения об именах, пространствах имён и сборках.

## Обработка ошибок

- Не создавать и не выбрасывать исключения в собственном коде для сообщения об ошибках. Для операций с результатом успех/неудача и валидации использовать `bool`, для асинхронных операций — `UniTask<bool>`: `true` означает успех, `false` — отказ или неудачу. Вызывающий код обязан проверять результат.
- Исключения внешних API перехватывать на границе интеграции, при необходимости логировать и преобразовывать в `false`, освобождая ресурсы. Не использовать повторный `throw`. Если существующий контракт требует `void` (например, `IInitSystem.Init()`), проверять результат вызываемых операций внутри этого метода или его асинхронного обработчика.

## Асинхронность и потоки

- Для асинхронного кода использовать UniTask (`Cysharp.Threading.Tasks`), а не `Task` как основной тип асинхронных операций.
- В проекте не использовать C# потоки: не создавать `Thread`, не запускать работу через `Task.Run`, `ThreadPool` или переключение UniTask в пул потоков. Асинхронную работу выполнять через UniTask в Unity PlayerLoop.
- Если `Task` необходим для совместимости с внешним API, предпочитать короткое имя `Task` с `using System.Threading.Tasks;` вместо полного `System.Threading.Tasks.Task`. При конфликте имён использовать alias; полное имя оставлять только при необходимости.

## Размещение кода и данных

- Временные рабочие файлы агента (скрипты проверок, логи, снимки и промежуточные результаты) создавать в корневой папке `tmp/`, исключённой из Git. Итоговые файлы проекта размещать в предназначенных для них папках.

- `Assets/App/Common/` — переиспользуемый код, переносимый между проектами. Не добавлять сюда зависимости от конкретной игры.
- Все новые конфиги и их данные размещать только в `Assets/Configs/`, при необходимости в подпапках по механикам. Не использовать `Assets/App/Configs/` для новых конфигов. Типы конфигов могут находиться рядом с механикой, как в существующих модулях.
- `Assets/App/Game/` — код конкретно этой игры.
- `Assets/App/Generation/` — алгоритмы и данные процедурной генерации; игровая интеграция данжа находится в `Assets/App/Game/Dungeon/`.
- Для новой механики создавать папку с её названием и подпапками `External/` и `Runtime/` в подходящем месте `Game/` или `Common/`.
- `Runtime/` — тестируемая бизнес-логика. В корне `Runtime/` новой механики должен находиться `.asmdef`; ссылки на сборки добавлять по необходимости.
- `External/` — код, сильно зависящий от Unity или связывающий большое количество механик. Такие классы обычно не планируется покрывать тестами.
- Держать бизнес-логику в `Runtime/`, а интеграцию — в `External/`. Не создавать зависимость `Runtime/` от `External/`.

## Сцены

- Сцены `StartScene`, `CoreScene` и `MenuScene` оставлять неизменными: не изменять их содержимое и настройки, не переименовывать, не перемещать и не удалять.
- При реализации механик и запуске инструментов настройки не вносить изменения в эти сцены, в том числе через Editor-скрипты или автоматическое сохранение Unity.

## Модульные объекты

- Для мобов, предметов, интерактивных и других модульных объектов использовать существующую систему `Assets/App/Common/ModuleItem/`. Расширять объект составом модулей, сохраняя общее ядро в `Common/`, а игровые реализации — в `Game/`.
- Для каждого определения модульного объекта создавать отдельный файл `ModuleItemGameConfig` (`.asset`) в `Assets/Configs/`. Настройки его модулей хранятся внутри этого файла. Несколько игровых экземпляров могут использовать один конфиг.
- Задавать непустой уникальный `Id` конфига в нижнем регистре; `Id` определяет конфигурацию, а `ReferenceSelf` — ссылку на данные конкретного экземпляра.
- Разделять настройки (`ModuleConfig`), изменяемое состояние (`IModuleData`) и поведение (`IModule`). Не сохранять состояние экземпляра в общем конфиге.
- Подключать модули через `IModuleSystem`: проверять наличие нужного конфига, использовать существующие данные или создавать начальные, затем добавлять поведение. Учитывать порядок `ModuleIndex` и очистку в `OnItemDestroyed`.
- При создании конфигов учитывать загрузку через Addressables с меткой `ModuleItemGameConfig` и существующий `ModuleItemAssetPostprocessor`. Имена assets должны давать уникальные адреса `ModuleItemGameConfig/{asset.name}`.
- Перед изменением модульной системы прочитать раздел «Модульная система объектов» в `docs/architecture.md` и соответствующие классы `Common/ModuleItem/`; примеры игровых модулей — `Game/Modules/Move/` и `Game/Modules/Health/`.

## Подключение механик

- Конфигураторы обычно размещать в `External/`; использовать существующий механизм `Configurator` для связывания зависимостей и регистрации в жизненном цикле.
- Пример: `Assets/App/Game/Player/External/PlayerConfigurator.cs`. Он связывает `PlayerController`, регистрирует его инициализацию в FSM и обновление в цикле Update. Текущий `PlayerController.Init()` создаёт игрока и размещает его в стартовой комнате данжа.
- Пример механики с отдельной Runtime-сборкой: `Assets/App/Game/Modules/Move/`.
- Добавлять только необходимые конкретной механике регистрации; не копировать регистрации FSM или Update без необходимости.

## Процедурная генерация

- Основной подход — сборка данжа из заранее сгенерированных комнат. Сохранять разделение шаблонов комнат, результата генерации и Unity-представления.
- Перед изменением генерации изучить `Assets/App/Generation/DungeonGenerator/` и игровую интеграцию в `Assets/App/Game/Dungeon/`.
- Использовать существующие конфиги комнат и префабы в `Assets/Prefabs/Tiles/Rooms/`; не подменять текущий подход другим алгоритмом без соответствующей задачи.

## Документация

- При изменении описанных архитектурных соглашений обновлять `docs/architecture.md` и соответствующие правила здесь.
- Отличать уже реализованное поведение от требований и планов. Не придумывать игровые механики и требования, которых пользователь не задавал.
- Сюжет и геймплей вести в `docs/game-design.md`: добавлять решения пользователя из чата; собственные идеи сначала предлагать в чате и включать в файл после их принятия пользователем.
