# Архитектура проекта

## Назначение и принципы

Проект — 2D RPG на Unity с пиксельной графикой.
Целевое разрешение экрана — 1920×1080. Размеры и вёрстка игрового UI
рассчитываются для этого разрешения. Оформление инвентаря находится
в существующем `Assets/Prefabs/Inventory/InventoryWindow.prefab`;
при изменении вёрстки сохраняются его сериализованные ссылки на представления
ячеек, контейнеры и кнопку закрытия.
Пиксельный шрифт Autumn Pixel находится в `Assets/Art/Fonts/AutumnPixel/`:
TTF, исходник геометрии и статический TMP-атлас 512×512 с русскими
и английскими символами. В InventoryWindow и ItemInfoWindow надписи
выводятся TMP-компонентами; исходные декоративные PNG сохранены.
Данж процедурно собирается из заранее сгенерированных комнат.
Целевое направление — хардкорная RPG в тёмном фэнтезийном сеттинге.
Конкретные механики сложности и детали сеттинга определяются отдельно.
Основной визуальный и игровой референс — Stoneshard. Референс не задаёт автоматически сюжет,
конкретные механики или технические решения: их требования уточняются отдельно.
При разработке соблюдаются SOLID и GRASP: ответственность распределяется
между небольшими связными классами, зависимости и связи между механиками
остаются явными. Простота решения важнее дополнительных абстракций.

## Обработка ошибок

В собственном коде не создаём и не выбрасываем исключения для сообщения
об ошибках. Проверки и операции возвращают `bool`, асинхронные операции —
`UniTask<bool>`. Значение `true` означает успех, `false` — отказ или неудачу;
вызывающий код проверяет результат и решает, что делать дальше.
Логирование дополняет возвращаемый результат.

Исключения внешних API перехватываем на границе интеграции,
при необходимости логируем, освобождаем ресурсы и возвращаем `false`
без повторного `throw`. Существующие контракты вроде `void IInitSystem.Init()`
сохраняются: внутри их обработчиков проверяется результат вызываемых операций.

## Асинхронность и потоки

Для асинхронных операций используем UniTask (`Cysharp.Threading.Tasks`)
с выполнением в Unity PlayerLoop. C# потоки в проекте не используем:
не создаём `Thread`, не используем `Task.Run`, `ThreadPool` и переключение
UniTask в пул потоков.

Основные типы асинхронных операций — `UniTask` и `UniTask<T>`.
Если внешний API требует `Task`, для совместимости используем короткое
имя `Task` с `using System.Threading.Tasks;`, избегая полного
`System.Threading.Tasks.Task`. Конфликт имён разрешаем через alias;
полное имя допускается только при необходимости.

## Структура приложения

Корень кода приложения — `Assets/App/`. Все новые конфиги и их данные
размещаются в `Assets/Configs/`, при необходимости в подпапках по механикам.
Остальные папки в `Assets/` могут содержать ресурсы и сторонние библиотеки.

| Папка | Назначение |
| --- | --- |
| `Assets/App/Common/` | Код, который переносится из проекта в проект. Не должен зависеть от кода конкретной игры. |
| `Assets/Configs/` | Все новые конфиги и их данные. Код механик сюда не помещается. |
| `Assets/App/Game/` | Код конкретно этой игры. Может использовать переиспользуемый код из `Common/`. |
| `Assets/App/Generation/` | Алгоритмы, конфиги и данные процедурной генерации данжа. |
| `Assets/App/Game/Dungeon/` | Создание игровых объектов данжа и интеграция с Unity. |
| `Assets/Prefabs/Tiles/Rooms/` | Подготовленные префабы комнат. |

Конфиги перенесены из `Assets/App/Configs/` в `Assets/Configs/`.
Оба редактора конфигов используют `Assets/Configs/` как корневую папку.
`ConfigWindow` загружает конфиги через `AssetDatabase`; если папки ещё нет,
показывает пустую коллекцию без файлового исключения.

Папка `Assets/Configs/` для данных не исключает типы конфигов внутри кода механик.
Например, `MoveModuleConfig` и конвертер находятся в
`Assets/App/Game/Modules/Move/Runtime/Config/`.

## Структура механики

Для новой механики создаётся папка с её названием:

```text
<Mechanic>/
├── External/
│   └── <Mechanic>Configurator.cs
└── Runtime/
    ├── <AssemblyName>.asmdef
    └── ... бизнес-логика ...
```

`Runtime/` содержит бизнес-логику, которую можно тестировать. В корне папки
располагается `.asmdef`, задающий сборку механики. Конкретное имя и ссылки
выбираются по соглашениям соседних модулей; например, модуль движения
использует `Autumn.Modules.Move.asmdef`.

`External/` содержит код, сильно зависящий от Unity или большого количества
механик: адаптеры, интеграцию, подключение к жизненному циклу и конфигураторы.
Автор проекта обычно не планирует тестировать эти классы.
Это не повод переносить туда самостоятельные игровые правила.

Интеграционный код использует бизнес-логику, а бизнес-логика не должна
зависеть от интеграционного кода в `External/`. Само имя `Runtime/` не означает,
что вся существующая сборка полностью свободна от любых типов Unity;
ключевой критерий — отделение тестируемых правил от сильных внешних зависимостей.

## Конфигураторы

Конфигуратор обычно находится в `External/` и подключает механику к приложению
через существующую инфраструктуру `Configurator`.

Эталон подключения: `Assets/App/Game/Player/External/PlayerConfigurator.cs`.
Этот класс наследует `Configurator`, отмечен атрибутом
`[Configurator(DIContext.CoreContext)]` и в `Configuration()`:

1. Вызывает `BindSingle<PlayerController>()` для связывания контроллера.
2. Регистрирует инициализацию через `RegisterFSM` на стадии `CoreInitStage`
   с порядком `StageOrders.PlayerController`.
3. Регистрирует контроллер в цикле обновления через `RegisterUpdate`, используя
   `UpdateStage.PlayerController`.

Текущий `PlayerController` реализует `IInitSystem` и `IUpdateSystem`.
В `Init()` он создаёт игрока, представление и размещает его в стартовой комнате данжа.

Набор регистраций зависит от потребностей механики. Например,
`Assets/App/Game/Modules/Move/External/MoveModuleConfigurator.cs` связывает
`MoveModuleSystem` в CoreContext, а отдельный `GlobalMoveModuleConfigurator`
регистрирует данные и конвертер в GlobalContext.

## Инициализация через IInitSystem

`IInitSystem` находится в
`Assets/App/Common/Utilities/Utility/Runtime/IInitSystem.cs` и содержит
синхронный метод `void Init()`. Система может быть обычным C#-классом:
наследование от MonoBehaviour и отдельный объект в сцене для её запуска не нужны.
Зависимости передаются через конструктор, а начальная настройка выполняется в `Init()`.

### Регистрация системы

В конфигураторе нужного DI-контекста выполняются две отдельные регистрации:

1. `BindSingle<T>()` связывает класс и его интерфейсы с одним экземпляром
   через `BindInterfacesAndSelfTo<T>().AsSingle().NonLazy()`.
2. `RegisterFSM<T>(stage, order)` записывает в `FSMRegistrar` тип системы,
   стадию запуска `FSMStage` и порядок `StageOrders`.

Одна только реализация `IInitSystem` или привязка в DI не запускает `Init()`.
Регистрация в FSM также не заменяет привязку экземпляра в DI.
Контекст выбирает контейнер системы, а стадия — момент вызова её инициализации.

Пример из `Assets/App/Game/Dungeon/DungeonCore/External/DungeonConfigurator.cs`:

```csharp
[Configurator(DIContext.CoreContext)]
public class DungeonConfigurator : Configurator
{
    public override void Configuration()
    {
        BindSingle<DungeonController>();
        RegisterFSM<DungeonController>(
            FSMStage.CoreInitStage,
            StageOrders.DungeonController);
    }
}
```

`DungeonController` реализует `IInitSystem`; FSM вызывает его `Init()`.
Регистрация в Update для инициализации не требуется.

### Порядок выполнения

1. `GlobalStartup` находит классы с атрибутом `ConfiguratorAttribute`,
   создаёт `ConfiguratorsManager` и общий `FSMRegistrar`.
   Конфигураторы GlobalContext выполняются при установке ProjectContext.
2. Соответствующий startup сцены в `InstallBindings()` вызывает
   `ConfiguratorsManager.RunConfigurator(...)`. Конфигураторы этого контекста
   выполняют `Configuration()`, добавляя DI-привязки и регистрации FSM.
3. После разрешения зависимостей Zenject вызывает обработчик `PostResolve`.
   Сначала выполняется `ConfiguratorsManager.OnResolved(...)`: здесь можно
   завершить связывание уже созданных систем.
4. Startup сцены получает из контейнера списки `IInitSystem` и
   `IPostInitSystem`, создаёт `StateMachine` с данными `FSMRegistrar`
   и добавляет нужный `DefaultState`. Для StartScene используется
   `StartInitStage`, для CoreScene — `CoreInitStage`, для MenuScene —
   `MenuInitStage`.
5. `StateMachine` группирует системы по зарегистрированным стадиям
   и сортирует их по возрастанию числового `StageOrders`.
   `SyncRun()` запускает добавленные состояния; `DefaultState.SyncRun()`
   последовательно вызывает `Init()` систем своей стадии.
6. После всех `Init()` этой стадии вызываются `PostInit()` систем,
   дополнительно реализующих `IPostInitSystem`. Их список тоже сортируется
   по зарегистрированному порядку.

Если одна система зависит от результатов синхронной инициализации другой,
она должна иметь больший `StageOrders`. При одинаковом значении порядка
очерёдность не гарантируется. Порядок выполнения конфигураторов не заменяет
порядок инициализации систем.

Сам `GlobalStartup` вызывает `OnResolved(GlobalContext)`, но не запускает
отдельный `StateMachine`. Поэтому привязку в GlobalContext нельзя считать
автоматической инициализацией глобальной стадии: вызов `Init()` определяется
регистрацией FSM и состояниями, которые запускает startup сцены.

### Асинхронная работа из Init

Текущая FSM синхронная: `Init()` не возвращает UniTask, а `SyncRun()`
не ожидает завершения асинхронных операций. При необходимости система
запускает отдельный метод, возвращающий `UniTask`, через `Forget`
с обработчиком ошибок. `async void Init()` для этого не используется.

Возврат из такого `Init()`, последующий `PostInit()` и завершение стадии
FSM не означают, что асинхронная загрузка уже закончилась.
Порядок `StageOrders` определяет порядок вызовов, но не ожидание UniTask.
Это нужно учитывать, если следующей системе нужен результат загрузки.

## Модульная система объектов

Для мобов, предметов, интерактивных и других модульных объектов используется
система `Assets/App/Common/ModuleItem/`. Объекты собираются из модулей:
общая инфраструктура остаётся в `Common/ModuleItem/`, а реализации игровых
возможностей находятся в `Assets/App/Game/Modules/`.

### Конфигурация объекта

- Для каждого определения модульного объекта создаётся отдельный
  `ModuleItemGameConfig` asset (`.asset`) в `Assets/Configs/`, при необходимости
  в подпапке. Все настройки модулей этого объекта находятся внутри его файла.
- Это конфигурация объекта, а не отдельный файл для каждого его появления
  в игре: несколько экземпляров могут использовать одну конфигурацию.
- `ModuleItemGameConfig` наследует `GameConfig` (`ScriptableObject`) и содержит
  `m_Id`, битовую маску тегов `m_Tags` и список `m_Modules`.
- `m_Modules` — полиморфный список наследников `ModuleConfig`, сериализуемый
  через `[SerializeReference]`. Настройки отдельных модулей не требуют
  самостоятельных assets. `ModuleItemGameConfigEditor` позволяет добавлять,
  удалять, переставлять модули и редактировать их поля в Inspector.
- `Id` конфига должен быть непустым и уникальным среди зарегистрированных
  конфигов. Используем нижний регистр: свойство `ModuleItemGameConfig.Id`
  и создание по строковому идентификатору приводят его к нижнему регистру,
  а поиск в контроллере конфигов выполняется по точному ключу.

Пример существующего файла — `Assets/Configs/Enemies/Player.asset`:
настройки модулей игрока хранятся в одном конфиге.
Для новых файлов действует путь `Assets/Configs/`.

### Настройки, состояние и поведение

| Часть | Ответственность |
| --- | --- |
| `ModuleConfig` / `IModuleConfig` | Настройки модуля, входящие в конфиг объекта. |
| `IModuleData` | Изменяемое состояние экземпляра; `GetModuleKey()` связывает его с контейнером данных. |
| `IModule` | Поведение модуля, подключаемое к объекту во время создания. |
| `IModuleItem` / `ModuleItem` | Доступ к конфигам, данным, поведению и тегам через `Get…`, `TryGet…`, `Has…`. |

Состояние экземпляра не записывается в общий конфиг. Например,
`HealthModuleConfig` задаёт максимальное здоровье, `HealthModuleData`
хранит текущее здоровье, а `HealthModule` предоставляет поведение.

`ModuleItem.Id` — идентификатор конфигурации, общий для экземпляров с одним
конфигом. `ReferenceSelf` — `DataReference` на данные конкретного экземпляра.
`ModuleItemData` хранит идентификатор конфига и ссылки на данные модулей.
`ModulesHolder` добавляет, восстанавливает и удаляет данные через
`IContainersDataManager`, поддерживая список этих ссылок.

### Создание и уничтожение

`IModuleItemsManager` предоставляет регистрацию конфигов, поиск конфигурации,
создание по `Id` или `DataReference` и уничтожение объекта. Создание по `Id`
создаёт новые данные, а создание по `DataReference` использует существующие.
`ModuleItemCreator` находит конфиг, восстанавливает данные модулей через
`ModulesHolder`, создаёт `ModuleItem` и вызывает обработчики создания.

`IModuleSystem` объединяет `ICreateModuleItemHandler` и
`IDestroyModuleItemHandler`. В `Init()` менеджер сортирует оба набора
обработчиков по возрастанию `SortIndex()` (`ModuleIndex`). Поэтому модули,
от которых зависит новый модуль, должны подключаться раньше него.
Порядок модулей в Inspector не заменяет этот порядок обработчиков.

Примеры — `MoveModuleSystem` и `HealthModuleSystem`: если соответствующего
конфига нет, обработчик возвращает объект без изменений. Если конфиг есть,
система получает существующие данные или создаёт начальные, после чего
добавляет поведение через `AddModule`. Существующее состояние при восстановлении
не должно перезаписываться начальными значениями из конфига.

`ModuleItem` отклоняет повторное добавление поведения, если модуль запрошенного
типа уже присутствует. Отсутствие модулей и ошибки создания передаются через
`bool`, `TryGet…` и `Optional<T>`; вызывающий код должен проверять результат.

`ModuleItemDestroyer` сначала вызывает `OnItemDestroyed` у обработчиков,
затем удаляет данные модулей через `ModulesHolder.Destroy()`.
Освобождение подписок и других ресурсов конкретной механики нужно учитывать
в её обработчике уничтожения.

### Подключение и загрузка

`ModuleItemsConfigurator` связывает менеджер и загрузчик, регистрирует их в FSM,
а в `OnResolved()` собирает обработчики создания и уничтожения из DI.
`GlobalModuleItemsConfigurator` регистрирует `ModuleItemContainerData`.
Конкретные системы модулей и контейнеры их данных подключаются конфигураторами
соответствующих механик.

Текущий `ModuleItemsConfigLoader` загружает `ModuleItemGameConfig` через
`IConfigLoader.LoadGameConfigs` по Addressables-метке `ModuleItemGameConfig`
и регистрирует их в менеджере с группой `Default`.
`ModuleItemAssetPostprocessor` при импорте конфигов добавляет их в группу
Addressables по умолчанию, задаёт адрес `ModuleItemGameConfig/{asset.name}`
и эту метку, если настройки Addressables доступны. Имена конфигов должны
обеспечивать уникальность адресов, даже при размещении в разных подпапках.

В системе также есть DTO и `IModuleDtoToConfigConverter` для JSON-пути,
но текущая инициализация `ModuleItemsConfigLoader` использует отдельные
ScriptableObject assets. Для новых объектов следуем этому подходу.

`ModuleItemView` — тонкая Unity-обёртка (`MonoBehaviour`) со ссылкой на
`IModuleItem`; бизнес-логику объекта следует оставлять в модулях.

### Размер предмета в инвентаре

`Game/Modules/ContainerItem/` содержит `ContainerItemModuleConfig` с целочисленными
`Width` и `Height` в ячейках инвентаря. Оба значения должны быть не меньше 1;
начальный размер — 1×1. Конфиг добавлен к `IronAxe`, `IronKey` и `IronSword`
в `Assets/Configs/Items/` и редактируется в списке модулей предмета.

`ContainerItemModuleSystem` подключает `ContainerItemModule` через `IModuleSystem`
и отклоняет некорректные размеры. Модуль предоставляет ширину и высоту из конфига.
`ContainerItemModuleData` хранит целочисленный `Index` позиции предмета в контейнере:
индексы начинаются с 0, значение -1 означает отсутствие предмета в контейнере.
Данные регистрируются в `ContainerItemContainerData`, а `ContainerItemModule.Index`
предоставляет доступ к текущему значению. При восстановлении модуль использует
существующие данные, не заменяя их начальными.
`Container` обновляет индекс при добавлении и удалении, а также сверяет индексы
с фактическими слотами при восстановлении. Изменение индекса выполняется до
уведомления `ItemChanged`, поэтому окно инвентаря видит актуальное состояние.
`ContainerModule.AddItem` принимает только экземпляры с подключённым
`ContainerItemModule`. Такое же ограничение действует в `Container.AddItem`
при добавлении по индексу; наличие одного конфига или данных недостаточно.
Отказ возвращается как `false`, без изменения слотов, индексов и уведомлений.
Обработчики переноса проверяют результат перед обновлением представления.
`Container` хранит предмет в верхней левой ячейке его прямоугольника. При выдаче
предмета он ищет первое свободное место по строкам и проверяет все ячейки
прямоугольника. Окна инвентаря и контейнера показывают по одной иконке на предмет
и позволяют взять его за любую занимаемую ячейку. Иконка под курсором сохраняет
размер и пропорции иконки в сетке. При клике по свободной ячейке многоклеточный
предмет занимает ближайший к курсору свободный прямоугольник, содержащий эту
ячейку. Перемещение и обмен проверяют границы и пересечения до изменения слотов.
Под иконкой лежащего предмета отображается непрозрачная тёмная подложка на всю
занимаемую площадь: она скрывает внутренние перегородки сетки, не перехватывает
клики и обновляется вместе с предметом при переносе и удалении.
По внешнему контуру подложки проходит чёрная обводка шириной 1 пиксель;
между соседними предметами она образует разделитель шириной 2 пикселя.
При переносе предмета зелёная подложка показывает его будущий прямоугольник
под курсором. Подсветка и ЛКМ используют общий выбор позиции, а проверка
`Container.CanMoveItem` применяется и для предпросмотра, и для перемещения
с обменом. Подсветка не меняет содержимое контейнера и не перехватывает клики;
при недопустимом размещении, выходе из сетки и завершении переноса она скрывается.
Подложки предметов, предпросмотр и иконки размещаются в общих слоях
`ItemVisuals/Backgrounds`, `ItemVisuals/Previews` и `ItemVisuals/Icons` над ячейками.
Все иконки рисуются после всех подложек,
поэтому подсветка не обрезает соседние предметы. Слои исключены из раскладки
сетки; положение и размеры визуальных элементов следуют за исходными ячейками.
В инвентаре наведение на любую занятую клетку находит якорь предмета,
окрашивает его подложку в серый и показывает `ItemInfoWindow` слева от всей
занимаемой области. Карточка берёт название из модуля имени, размер из
`ContainerItemModule` и тип из конфига при его наличии. Карточка не принимает
клики и скрывается при переносе, выходе с предмета или закрытии инвентаря.
При наведении на надетый предмет эта же карточка привязывается к слоту
экипировки и показывает плашку «ЭКИПИРОВАНО».
При загрузке контейнер использует
размеры сетки из конфига владельца и ищет новое место для сохранённых предметов,
чьи размеры больше не позволяют оставить их в прежних ячейках.

### Слоты экипировки

`Game/Modules/Equipment/` подключает `EquipmentModule` через `IModuleSystem`,
если у владельца есть `EquipmentModuleConfig`. В `Player.asset` заданы
11 уникальных слотов. В Inspector допустимые типы каждого слота выбираются
из списка значений `EquipmentType`. Старые строковые списки преобразуются при
загрузке. `EquipmentModule.CanEquip` сопоставляет строковый тип из
`EquipmentItemModuleConfig` предмета со значением enum. Оба кольца используют тип `Ring`,
обе руки допускают `OneHanded` и `TwoHanded`, ожерелье использует `Amulet`, плащ —
`Shoulder`.
`EquipmentModule.TryEquip` занимает свободный совместимый слот конкретным
экземпляром. Предмет из инвентаря владельца при этом удаляется из контейнера.
Система экипировки подключается после `ContainerModule`. Модуль подписывается
на `Container.ItemAdded` контейнера владельца и экипирует добавленный предмет
в первый свободный совместимый слот по порядку правил конфига. Перемещение
внутри контейнера и восстановление его содержимого не отправляют `ItemAdded`.
При уничтожении владельца модуль снимает подписку.
Занятые слоты, повторное надевание того же экземпляра и предметы из чужого
контейнера отклоняются без изменений. `TryGetEquippedItem` читает слот,
`TryUnequip` освобождает его и возвращает предмет вызывающему коду. Успешные
изменения отправляют `SlotChanged`. `EquipmentModuleData` хранит ссылки
`DataReference` по ключам слотов, а экземпляры восстанавливаются при чтении.
При создании игрока `InventoryController` привязывает его `EquipmentModule`
к верхней панели `InventoryWindow`. Предметы переносятся между экипировкой
и рюкзаком кликом или отпусканием ЛКМ. Зелёный предпросмотр использует те же
проверки, что и размещение. `TryUnequipToInventory` снимает предмет только
при наличии места по выбранному индексу в контейнере владельца. Добавление
при снятии экипировки оставляет предмет в рюкзаке. Иконки
экипировки обновляются по `SlotChanged`. Их размер и пропорции рассчитываются
по ячейкам рюкзака и размеру предмета из `ContainerItemModule`. Иконка
центрируется в слоте экипировки.

### Выдаваемые предметы

`Game/Modules/IssuedItems/` добавляет модуль `IssuedItemsModuleConfig` в конфиг
игрока. В списке `Entries` каждая запись содержит ссылку на `ModuleItemGameConfig`
предмета и количество `Quantity` (не меньше 1, по умолчанию 1). Старый список
ссылок загружается как записи с количеством 1 в исходном порядке.
Настройки хранятся внутри `Assets/Configs/Enemies/Player.asset`.

`IssuedItemsModuleSystem` подключает поведение и данные через `IModuleSystem`.
Он только добавляет модуль и не создаёт предметы в обработчике создания объекта.
`PlayerController` вызывает `TryIssueItems` после создания всех модулей игрока.
Предметы создаются через `IModuleItemsManager` и добавляются через `ContainerModule`
этого игрока. Совместимые стартовые предметы автоматически надеваются в
свободные слоты экипировки. При отсутствии `ContainerModule`
выдача возвращает `false`. `ContainerModule.AddItem` возвращает `bool`:
`false` означает отсутствие свободного слота или недопустимый предмет.
Жёстко заданная выдача меча из `InitHandItems` удалена; прежний меч
перенесён в список игрока.

`IssuedItemsModuleData` хранит число успешно выданных экземпляров в отдельном
`IssuedItemsContainerData`. Повторный вызов или восстановление тех же данных
не выдаёт их заново. При отказе выдача возвращает `false`, сохраняет прогресс
и удаляет созданный, но не добавленный предмет. Если конфиг остался прежним,
новый вызов продолжает с первого невыданного экземпляра, в том числе внутри записи.
Состояние относится к экземпляру игрока; текущий `PlayerCreator` по-прежнему
создаёт новый экземпляр при инициализации, а не восстанавливает игрока из сохранения.

## Перемещение игрока

`PlayerMoveController` читает двумерный ввод и получает скорость из существующего
`MoveModule`. Скорость применяется к `Rigidbody2D.linearVelocity` в плоскости XY,
без пересчёта относительно камеры и поворота Transform в 3D. Диагональный ввод
нормализуется; замедление во время атаки сохраняется.

В `Player.prefab` движение использует динамический `Rigidbody2D` без гравитации
с заблокированным вращением и `CapsuleCollider2D`. Начальная позиция игрока
переводится из координат данжа в `(X, Y, 0)`. `MoveAnimationPresenter` управляет
параметрами `IsWalkingLeft` и `IsWalkingRight` контроллера `AutumnHero2D`;
при движении по вертикали сохраняется последнее горизонтальное направление.
При отсутствии движения оба параметра ходьбы выключаются, и Animator переходит
в idle для соответствующего направления. Параметр `WeaponEquipped` переключает
клипы ходьбы и покоя с `AutumnHero_Base_*` на `AutumnHero_OneHanded_*`.

`HandItemsController` обновляет параметр и спрайты `WeaponNear` и `WeaponFar`
при изменении слотов рук. Одноручное оружие задаёт оба спрайта в
`OneHandedWeaponModuleConfig`. Сначала проверяется правая рука, затем левая.
При ЛКМ в игровом мире `PlayerAttackController` фиксирует конфиг оружия и
сторону удара до контакта. `PlayerMeleeAttackState` один раз отправляет
событие контакта, а после окончания удара управление возвращается к ходьбе
или idle.
Оба клипа удара управляют дочерним `SwordSlashTrail`. Белая дуга достигает
пика на кадре контакта, зеркалится при ударе влево и скрывается до конца клипа.
`MeleeAttack2D` в этот момент ищет все живые цели в прямоугольнике
перед игроком. Препятствия проверяются по твёрдым 2D-коллайдерам отдельно
для каждой цели. Сколько бы коллайдеров существа ни попало в зону, взмах
передаёт ему один `HitModel` через `IDamageHandler`. Урон, дальность и ширина
зоны хранятся в `OneHandedWeaponModuleConfig`.
Там же `AttackSpeed` задаёт положительный конечный множитель скорости удара:
1 сохраняет исходную скорость клипа, 2 ускоряет удар вдвое, 0,5 замедляет вдвое.
`PlayerAttackController` и `EnemyCombat2D` фиксируют его в Animator-параметре
`AttackSpeed` при запуске каждого удара. Параметр подключён только к
`AttackLeft`/`AttackRight` контроллеров `AutumnHero2D` и `Deserter`, поэтому
не меняет скорость перемещения и смерти. Контакт по нормализованному времени
клипа и завершение атаки автоматически следуют новой скорости; смена оружия
во время удара применяется к следующей атаке. Некорректная скорость
отклоняется перед запуском удара. Старые 3D-контроллеры этим параметром
пока не управляют.
`MeleeAttackView` показывает зону для `IronShortsword` с обеих сторон героя,
когда выбран префаб игрока. У `Skeleton` дочерний `Hurtbox2D` связан
с существующим `SimpleDamageHandler`.

`CameraFollowController` следует за игроком по обеим осям плоскости XY,
сохраняя координату Z корня камеры и глубину дочерней ортографической камеры.

## Дезертир

`Deserter.asset` с идентификатором `deserter` задаёт представление,
здоровье, скорость и параметры удара. При создании через `AIController`
дезертир движется через `MoveModule` и `Rigidbody2D` в плоскости XY.
Тело врага при инициализации переводится в `Kinematic`: игрок не может
сдвинуть его столкновением. Перемещение выполняется через `Rigidbody2D.Slide`,
который проверяет препятствия и сохраняет столкновения со стенами и существами.
`Game/Modules/AI/` содержит `AIModuleConfig`, `AIModule` и `AIModuleSystem`.
Конфиг AI входит в список модулей `Assets/Configs/Enemies/Deserter.asset`:
`DetectionRadius` задаёт радиус обнаружения (5 юнитов), `TargetScanInterval` —
интервал поиска новой цели (0,2 секунды). Неположительные и нечисловые значения,
включая бесконечность, отклоняются при создании модульного объекта.
`AIModuleConfigurator` регистрирует систему в CoreContext. `AIModuleSystem`
добавляет поведение только объектам с AI-конфигом; зависимостей от других
модулей у него нет (`ModuleIndex.Default`). Отдельные сохраняемые данные
пока не требуются: модуль предоставляет настройки, а цель, таймер поиска
и активное состояние принадлежат конкретному контроллеру врага.
Настройки AI не дублируют скорость из `MoveModuleConfig` и параметры удара
из `OneHandedWeaponModuleConfig`. `AIViewController` проверяет наличие
`AIModule` перед запуском 2D-врага. `EnemyCombat2D` читает его настройки
и меняет направление через параметры существующего контроллера `Deserter`.

Поведение 2D-врага использует существующие контракты `IAIState` и
`IUpdateState` и переключение `Exit → Enter` в `AIViewController.SetState`.
`IdleAIState2D` останавливает врага, если цели нет; `RunAIState2D`
двигает его к цели через `MoveModule` и `Rigidbody2D`; `AttackAIState2D`
останавливает движение и запускает удар. `EnemyCombat2D` предоставляет
операции движения и боя и выбирает следующее состояние по доступности цели.
Начатый удар удерживает состояние атаки до события завершения анимации;
после него цель проверяется заново. При смерти выполняется выход из
текущего состояния, переход в существующий `DeadAIState` и снятие
подписок на события атаки. Прежние состояния 3D-врагов сохранены.

Дезертир запускает подходящий клип атаки, когда игрок доступен для удара.
В точке контакта `MeleeAttack2D` заново проверяет коллайдер игрока
и препятствия. При смерти дезертир останавливается, его коллайдеры
отключаются, а Animator проигрывает смерть в текущую сторону.

## Чит-панель

Существующая uGUI-панель `CheatsWindow` открывается и закрывается действием
`UI/Cheats`, привязанным к клавише `\` (`<Keyboard>/backslash`). `OpenCheatsSystem`
снимает подписку при уничтожении DI-контекста. Панель создаётся лениво через
существующий Addressables-адрес `CheatsWindow` на меню-канвасе.
Тёмный фон с альфой 0.65 растянут на весь экран. Прокручиваемый список берётся
из зарегистрированной группы конфигов `Default` и включает только определения
с `ContainerItemModuleConfig`; записи отсортированы по Id. Ячейка показывает
иконку при её наличии, Id и размеры в слотах. Список расположен одним столбцом
в скроллере в левой четверти панели. Выбранная кнопка не сохраняет подсветку;
навигация между кнопками отключена, наведение мыши выделяется отдельно.
Список создаётся один раз при
первом открытии, повторное открытие не дублирует ячейки.
Нажатие создаёт новый экземпляр через `IModuleItemsManager` и добавляет его
в `ContainerModule` игрока. При отказе добавления экземпляр уничтожается;
система экипировки при выдаче не вызывается. Старый выбор места выдачи скрыт.

Окно инвентаря привязано к контейнеру игрока через `InventoryController.BindContainer`
после создания игрока. `Container.ItemChanged` обновляет отображаемые слоты;
добавление и удаление через `InventoryService` меняют этот же контейнер.
`InventoryService` создаёт пустую модель сетки до привязки и берёт предметы только
из контейнера игрока. Отдельные данные `InventoryData` больше не загружаются
окном и не используются как источник предметов; добавление до привязки отклоняется.
Количество слотов контейнера должно совпадать с сеткой окна;
иначе привязка возвращает `false`. Подписки снимаются при уничтожении контекста.

## Перенос предметов

`DragItemController` показывает иконку переносимого предмета после клика по
слоту или начала перетаскивания с зажатой ЛКМ. Для удержания `ItemSlotView`
использует события начала и конца перетаскивания Unity. Отпускание над ячейкой
использует те же правила размещения, что и клик. При недопустимом отпускании
предмет остаётся в исходном слоте. Позиция мыши читается через `Mouse.current` нового
Input System, а `ItemView` преобразует её в позицию на Canvas через
`RectTransformUtility.ScreenPointToWorldPointInRectangle` с учётом режима
канваса и его камеры. Позиция обновляется сразу при выборе и каждый кадр.
Графика переносимой иконки не перехватывает UI-raycast.

## Неизменяемые сцены

`CoreScene` и `MenuScene` оставляем неизменными: их содержимое, настройки,
имена и расположение сохраняются, включая работу Editor-скриптов и сохранение Unity.
Пользователь разрешил изменять `StartScene` для редакторской проверки генерации
через `DungeonGenerati`: изменения ограничиваются генератором и его результатом,
остальные объекты и настройки сохраняются. Для остальных задач `StartScene`
также остаётся неизменной. Новые механики подключаются без изменения сцен.

## Процедурная генерация данжа

### Основной подход

Данж собирается процедурно из заранее сгенерированных комнат.
Подготовка комнаты и сборка общего данжа — отдельные задачи:
шаблон описывает комнату, а генерация выбирает и размещает её экземпляры.
Unity-представление создаётся отдельно от результата работы алгоритма.

### Содержимое префаба комнаты

Корневой объект комнаты имеет только обязательный `Transform`. У него две
дочерние группы: `[STATIC]` для постоянной геометрии комнаты и `[DYNAMIC]`
для ломаемых бочек, врагов и других объектов, которые меняются во время игры.
Нужные компоненты находятся на дочерних объектах.

В 2D-префабах сетка содержит слои `Floor`, `Walls` и `BottomWalls`.
Передний контур размещается в `BottomWalls`.

```text
Комната
├── [STATIC]
│   └── Grid
│       ├── Floor
│       ├── Walls
│       └── BottomWalls
└── [DYNAMIC]
```

У комнаты без динамического содержимого группа `[DYNAMIC]` пустая.

Порядок отрисовки 2D-данжа задаётся через `Order in Layer`.

| Объект | Порядок |
| --- | ---: |
| Пол (`Floor`) | 0 |
| Верхние стены (`Walls`) | 100 |
| Верхние и боковые двери | 200 |
| Игрок | 300 |
| Нижние двери | 400 |
| Нижние стены (`BottomWalls`) | 500 |

Под проходимой частью горизонтальных тайлов переднего контура продолжается пол.
Рендерер `BottomWalls` выводит стены поверх персонажей и предметов.
Для отражённых угловых тайлов `BottomWalls` использует `Sprite-Lit-Default`.
Горизонтальная кладка переднего контура занимает 60 пикселей тайла и
совпадает по видимой высоте с верхними стенами.
Тайлы набора `SouthWalls` используют контуры коллизии спрайтов. У горизонтальных
проходимых участков коллайдер занимает нижние 16 пикселей клетки, а на внешних углах
соединяется с узкой вертикальной полосой боковой стены. Тайлсет добавлен в
палитру `Autumn Dungeon`.
В клетках стыка, которые могут совпадать со стеной соседней комнаты, используются
варианты южной кладки со сплошным коллайдером.

Для точечного появления врага используется компонент `EnemySpawner` на
дочернем объекте `[DYNAMIC]`. В поле `Enemy` задаётся конфиг модульного врага.
После инъекции Zenject компонент один раз создаёт врага через `IAIController`
в позиции объекта при вызове `Start()`. В `StartRoom2D_16x15` так размещён дезертир.
Спавн выполняется в игровом экземпляре комнаты, где доступен `IAIController`.

### Текущая кодовая основа

- Настройки генерации хранятся в ScriptableObject
  `Assets/Configs/Dungeon/GenerationConfig.asset` (тип `GenerationConfig`).
  Asset загружается через `IConfigLoader.LoadGameConfig` по Addressables-адресу
  `GenerationConfig`; затем `GenerationConfigConverter` проверяет настройки
  и создаёт runtime-конфиги. В конфиге оставлены только используемые
  настройки: ключ генерации, ссылки на комнаты, максимальная глубина
  и лимит итераций `TileBasedDungeonGenerator`, а также галочка
  «Запретить вращение комнат». При включённой галочке алгоритм рассматривает
  только поворот 0°; в текущем конфиге она включена. Разделы создания случайных
  комнат, разделения, отбраковки маленьких и пограничных комнат,
  а также квадратного разбиения удалены из конфига.
  Новые assets создаются через `Create → Autumn → Dungeon → Generation Config`.
- Типы настроек генерации находятся в `Runtime/Configs/Settings` и используют
  имена без `Dto`, включая `DungeonGenerationConfig`, настройки отдельных
  алгоритмов и `SizeInt`. Они сериализуются Unity внутри ScriptableObject;
  JSON-атрибуты и неиспользуемые JSON-обёртки удалены.
  `DungeonGenerationConfigConverter` создаёт runtime-конфиг из этих настроек.
- Каждому 2D-префабу соответствует отдельный `DungeonRoomConfig` asset
  в `Assets/Configs/Dungeon/Rooms/2D/Start|Transit|Content/`.
  В нём находятся уникальный `Id`, тип комнаты, границы Tilemap с учётом
  стен, вход, список выходов и `AssetReferenceGameObject` на префаб.
  Новые assets создаются через `Create → Autumn → Dungeon → Room Config`.
  В `GenerationConfig.asset` поле `TileBasedGenerationSettings.Rooms`
  содержит прямые ссылки на эти конфиги, без встроенных описаний комнат.
  Сейчас подключены все десять 2D-комнат; конфиги 3D-комнат не создавались.
- Координаты дверей в room asset заданы в локальных клетках Tilemap:
  левая клетка горизонтального или нижняя клетка вертикального проёма.
  Для стартовой комнаты верхний проём выбран внешним входом; боковые —
  выходами. У промежуточных комнат входом выбрана левая дверь, если она
  есть, иначе нижняя. У контентных комнат единственная дверь — вход.
  Перед генерацией координаты нормализуются относительно `Bounds.min`;
  runtime-данные создаются отдельно и не меняют ScriptableObject.
  При повороте учитываются обе клетки дверного проёма.
- Префабы 2D-комнат зарегистрированы в Addressables. Игра передаёт ссылку
  из runtime-данных в `IAssetManager`, редактор получает префаб через
  `editorAsset`. Room configs загружаются как зависимости основного
  Addressables-конфига; отдельная регистрация каждого room asset не нужна.
- `MonoDungeonGenerator` принимает ScriptableObject и ключ генерации.
  Если asset не назначен, его Inspector использует указанный конфиг по умолчанию
  без изменения компонента или сцены. Старые поля компонента и файл
  `Assets/Configs/Jsons/GenerationConfig.json` сохранены для сериализованных
  ссылок защищённых сцен; генерация больше не читает этот JSON.
- `Assets/App/Generation/DungeonGenerator/Runtime/` содержит генераторы,
  конфиги и модель результата генерации; сборка — `Autumn.DungeonGenerator`.
- `DungeonGenerator` формирует последовательность шагов. Сейчас конструктор
  выбирает `Generation2()`, где активен `TileBasedDungeonGenerator`.
- `TileBasedDungeonGenerator` выбирает комнаты и варианты из конфигурации,
  начинает со стартовой комнаты и строит ветви через выходы комнат.
  Используются только `Start`, `Transit` и `Content`: у стартовой вход
  относится к внешней локации, у промежуточной есть вход и хотя бы один
  выход, у контентной есть только вход. Двери не должны дублироваться.
  `Content` объединяет прежние `End` и `Chest` по роли в сборке.
  На предельной глубине ветвь закрывается контентной комнатой. Она также
  может закрыться раньше, если промежуточные комнаты не подходят.
  Лимит `MaxOutputs` удалён вместе с отдельным типом `End`.
  Неудача построения стартовой ветви возвращает отказ генерации;
  достижение лимита итераций отклоняет очередную попытку построения
  без исключения. Поле результата `EndGenerationRoom` пока сохраняет
  последнюю контентную комнату для совместимости с игровой моделью;
  отдельного типа конечной комнаты больше нет.
- `Assets/Prefabs/Tiles/Rooms/` содержит наборы `2D/` и `3D/`.
  В `2D/` комнаты распределены по `Start/`, `Transit/` и `Content/`.
  Мастерские сгруппированы в подпапках `Workshops/` соответствующего типа;
  При классификации широкий непрерывный проём считается одной дверью.
  Все проёмы 2D-комнат имеют ширину ровно два соседних тайла вдоль стены.
  При расширении проёма локально корректируются примыкающие стены и узкий
  подход, чтобы он также оставался двухтайловым; число дверей сохраняется.
  Входы и выходы выступают из прилегающей стены на один тайл пола.
  На внешнем крае каждого выхода расположен связанный экземпляр
  `WorkshopDoorVertical` или `WorkshopDoorHorizontal` из
  `Assets/Prefabs/Tiles/Structures/2D/`, внутри `[DYNAMIC]`.
  У каждого дверного префаба два дочерних объекта со `SpriteRenderer`,
  `FirstLeaf` и `SecondLeaf`. `Animator` на корне переключает спрайты обеих
  створок. `FirstLeaf` задаёт отражение по X и порядок отрисовки всей двери.
  На входящих проёмах дверных объектов нет; контентные комнаты без дверей.
  Двери должны открываться внутрь. Вертикальная дверь на правой стене
  отражается по X; для левой используется исходная ориентация.
  По правилу настройки дверей `flipY` не используется, включая нижние
  выходы. Прежнее указание отражать нижние двери по Y отменено.
  Оба дверных префаба используют материал URP `Sprite-Lit-Default`.
  `Mesh2D-Lit-Default` для них не применяется: отражённые двери с ним
  не отображаются. Визуальная проверка отражений выполняется с реальным
  материалом префаба, в закрытом и открытом состояниях.
  При изменении проёмов синхронизируются `Bounds`, `InputDoor` и
  `OutputDoors` соответствующего конфига комнаты.
  Старые 3D-префабы сохранены, но в текущую генерацию не подключены.
  `MonoDungeonGeneratorEditorV4` и игровой `RoomController` используют
  `RoomPlacement` для размещения комнат в XY и вращения вокруг Z.
  Повороты алгоритма по часовой стрелке соответствуют отрицательному углу
  Unity. Положение компенсирует `PrefabOrigin` и смещение клетки при повороте
  Tilemap вокруг корня префаба.
  `Generate` создаёт связанные экземпляры внутри дочернего `Rooms` объекта
  генератора, `Clear` очищает только этот контейнер. Обе операции поддерживают
  Undo; подписки редактора корректно снимаются при закрытии Inspector.
  Тайлы исходных префабов при сборке не дополняются и не изменяются.
  Вход новой комнаты ставится на одну клетку внутрь от внешней опорной
  клетки выхода предыдущей: готовые выступы пола соединяются напрямую,
  без добавочного участка между ними. Для пары непосредственно связанных
  комнат проверка `Bounds` допускает общую двухклеточную полосу пустой
  границы проёмов и торцов стен; остальные комнаты проверяются обычным
  пересечением границ. Сценовые подписи учитывают
  реальные трансформации комнат. Генерация синхронная, без асинхронного
  обработчика, который мог бы продолжить работу после закрытия Inspector.
  Навигация по-прежнему использует прежнее представление XZ.
- `Assets/App/Game/Dungeon/DungeonCreator/` отвечает за создание игровой
  модели данжа, комнат и их содержимого.
- `Assets/App/Game/Dungeon/DungeonCore/` содержит контроллеры и Unity-интеграцию.
  `DungeonController.Init()` создаёт данж через `IDungeonCreator`, затем
  создаёт сервис и контроллеры представления.
- В игровом режиме `DungeonController` сначала размещает все комнаты под
  неактивным корнем данжа. Затем контейнер Zenject из `CoreContext`
  рекурсивно внедряет зависимости в `[DYNAMIC]` каждой комнаты, включая
  неактивные объекты. После инъекции контроллер активирует данж и запускает
  инициализацию интерактивных объектов и спавн врагов.
- `CreatingModuleItemView` наследуется от `ModuleItemView` и хранит ссылку
  на `ModuleItemGameConfig`. Редактор автоматически записывает `ObjectId`
  в размещение внутри `[DYNAMIC]` префаба комнаты и назначает отдельный ID
  копии при дублировании. При переносе и переименовании ID сохраняется.
- До активации комнаты `RoomController` связывает эти компоненты с игровыми
  экземплярами. `RoomData` хранит соответствие `ObjectId` и `DataReference`.
  `RoomService` создаёт экземпляр по конфигу при отсутствии записи или
  восстанавливает его по сохранённой ссылке. Ошибка восстановления прерывает
  привязку. Запись данжа на диск и его загрузка при входе пока не подключены.
- `DoorInteractiveView`, `ChestInteractiveView` и `ContainerInteractiveObject`
  используют общий `InteractableView`. По клику `ContainerInteractiveObject`
  берёт `ContainerModule` привязанного экземпляра и открывает его сетку в
  `ContainerWindow`. Если задан `IssuedItems`, модуль заполняет контейнер при
  первом открытии и хранит прогресс выдачи. Окно использует графику инвентаря
  Autumn, показывает его рядом и закрывается вместе с ним. `ClosePopWindowService`
  обрабатывает `Esc`: сначала закрывает верхнее окно, а при отсутствии
  закрываемого окна передаёт действие меню паузы.
- Наведение на 2D-объект определяется по границам видимых `SpriteRenderer` из
  `InteractableView` с учётом порядка отрисовки. Подсветка рисуется поверх
  объекта по общей маске его спрайтов и исчезает при уходе курсора или
  открытии игрового окна.
- `InteractionController` в `CoreContext` хранит включённые представления и
  текущую цель под курсором. `InteractableView` получает этот контроллер
  через Zenject и регистрируется на время активности. Обработчик клика
  игрока и подсветка используют текущую цель из того же контроллера.
- `DoorController` переключает состояние `DoorModule` по клику и применяет
  его к параметру `Opened` аниматора и коллайдеру, который перекрывает проход.
- В `StageOrders` инициализация `DungeonController` имеет порядок `100`,
  а `PlayerController` — `200`. Игрок создаётся после инициализации данжа
  и размещается в стартовой комнате.

В кодовой основе сохранены другие варианты и шаги генерации: разбиение,
триангуляция, остовное дерево, коридоры и другие. Наличие этих классов
не означает, что они включены в текущую последовательность генерации.
При изменениях проверять активный набор шагов в `DungeonGenerator`.

### Соглашения для изменений

Сохранять разделение алгоритма сборки, данных результата и создания
Unity-объектов. Расширять существующие конфиги и шаблоны комнат по задаче.
Новые конфиги и их данные размещать в `Assets/Configs/`.
Не добавлять сюжет, локации или правила из других игр на основании
общей кодовой основы или референса.

## Текущий этап

Новые тесты пока не пишем: проект на ранней стадии. При этом сохраняем
возможность тестировать бизнес-логику из `Runtime/` в будущем.
Это правило не требует удаления уже существующих тестов.

Описанная структура — соглашение для дальнейшей разработки.
Существующие папки могут быть организованы неполно: например, у `Player/`
сейчас есть `External/`, но нет отдельной папки `Runtime/`.
Само добавление документации не требует перестраивать существующий код.
